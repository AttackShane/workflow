## 为什么需要"本地化"的 Coze 工作流编辑器？

先说痛点。Coze 官方编辑器在浏览器里跑，但它本质是"云端 SaaS + 联网协作"形态。一旦你的工作流变多、变复杂，几个问题会同时冒出来：

- 版本失控：工作流改了什么、谁改的、上一版长啥样，网页里没有 Git 那种清晰 diff。回滚只能靠手动另存。
- 编辑卡顿：节点一多，云端画布的拖拽和缩放就开始掉帧，尤其弱网环境下。
- 无法进代码库：你想把工作流当"配置即代码"用，用 PR Review 流程管变更，但官方只给你网页手写 JSON，没有可读的本地格式。
- 协作受限：离线、内网、对数据出公有云有合规要求的团队，根本没法把核心工作流放上去。

这四类需求，云端编辑器天生够不着。于是，把编辑器搬回本地，就成了绕不开的需求。

## 这个项目是什么

它本质上是一个零框架依赖、纯原生 JavaScript（ES Module）实现的 Coze 工作流可视化编辑与转换工作台，三页面覆盖管理、转换、编辑，单文件 HTML 双击即可离线运行。

这个项目最初是棱镜智汇团队在管理大量 Coze 工作流时打磨出来的内部小工具。当时他们手上躺着几十个工作流，困境很具体——

> **故事 1：几十个工作流压垮了网页**
> 去年双十一前，棱镜智汇的对话算法组要同时维护 40 多个 Coze 工作流。负责人阿杰每周最怕两件事：一是某条工作流在云端改崩了，想回滚却找不到上一版；二是产品要批量把 30 个工作流里的模型从旧版换成新版，他只能在网页里一个个点开、手改、再保存，两天还没改完一半。更头疼的是，团队想用 Git 管理这些工作流，但官方只给网页手写 JSON，根本没法做 diff 和 Review。"我们只是想要一个能本地打开、能导出可读 YAML、能拖拽改节点、还能离线跑的工具，"阿杰说，"但市面上根本没有。"这个内部小工具，就是被这些日常糟心事硬逼出来的。

说白了，它就是开发者给自己做的趁手工具。

## 三页面功能详解

工作台分三个页面，对应工作流生命周期的三步。

### 管理页：本地工作流清单

管理页是入口。你可以在这里集中浏览、搜索、打开本地工作流文件，支持按名称/节点数/最近修改时间排序。它还内置版本对比和小地图，让你一眼掌握画布全貌。对有多工作流要维护的团队，这页相当于一个本地"工作流资源管理器"。

### 转换器：YAML↔Coze 双向互转

这是项目的核心差异点之一。转换器支持 YAML 与 Coze 工作流格式双向转换——既可以把线上导出的 Coze JSON 转成可读 YAML，也能把 YAML 反向生成可导入 Coze 的格式。语法高亮由 Web Worker 在后台完成，不卡主线程。

> **故事 2：30+ 节点工作流，靠 YAML diff 半小时改名改模型**
> 阿杰后来真正用上这个可视化编辑器，是在一次模型迁移里。他把线上一个 32 节点的客服工作流导出，丢进转换器，几秒得到一份带缩进、带注释的 YAML。然后他直接在编辑器里用全局替换，把 32 处旧模型名一次性改成新版本，又顺手把三个写死的提示词变量统一命名。改完用转换器导回 Coze 格式，前后不到半小时。如果用网页手改，同样的活至少要大半天，还容易漏。"最爽的是 YAML 能进 Git，"他说，"以后谁改了什么，PR 里一行行 diff 看得清清楚楚。"

### 编辑器：可视化拖拽

编辑器页是真正的"拖拽画布"。你可以用鼠标拖出节点、拉连线、框选多个节点批量移动，撤销/重做支持 50 步，还有键盘快捷键、深浅主题、中英文 i18n 切换。它支持 SVG 导出，方便把工作流贴进文档或 Wiki。

## 支持 50 种节点类型的 Coze 工作流编辑器

这是和通用流程图库拉开差距的关键。这个 Coze 工作流编辑器内置 50 种 Coze 专属节点类型，覆盖从大模型到数据库的完整能力面：

| 分类 | 代表节点（type） | 说明 |
|------|------------------|------|
| 大模型 | `llm` | 调大模型生成/推理 |
| 代码 | `code` | 执行代码片段 |
| 知识库 | `knowledge_query` | 检索知识库 |
| 逻辑 | `condition` / `loop` / `batch` | 条件、循环、批处理 |
| 网络 | `http` | 调用外部 HTTP 接口 |
| 数据库 | `db_read` / `db_write` / `db_insert` / `db_delete` | 多种数据库操作 |
| 记忆 | `memory_read` / `memory_write` | 读写对话记忆 |
| 多模态 | `video` / `image` / `audio` | 视频/图像/音频处理 |
| 流程 | `start` / `end` / `selector` / `message` | 起止、选择器、消息 |

和通用流程图库摆在一起看：Logic Flow、Drawflow 通常只提供约 13 类通用图形节点，并不理解 Coze 的语义（可参考 [Logic Flow 官方站点](https://site.logic-flow.cn/) 与 [Coze 官方工作流文档](https://www.coze.cn/open/docs/)）；后端 CLI 转换器（agentbridge、coze-workflow-parser）能解析节点，但完全不提供可视化。本项目把"Coze 语义 + 50 节点 + 可视化"三者合一。

## 性能是怎么做到丝滑的？

很多"纯前端"编辑器一上大画布就卡。这个本地管理工具用了四招：

1. 虚拟滚动：只渲染视口内可见的节点和连线，离屏节点不占 DOM。
2. Web Worker 语法高亮：YAML/JSON 的着色计算放到后台线程，主线程专注交互，不卡输入。
3. 无限画布 + 视口剔除：拖到画布任意位置都不丢帧，视口外的元素直接跳过绘制。
4. 批量 DOM 测量：对 N 个节点做尺寸测量时，合并成一次 reflow，而不是每个节点触发一次重排——这是大画布不掉帧的核心。

> **故事 3：500+ 节点也不卡**
> 棱镜智汇后来把一个超长的事实核查工作流塞进编辑器做压测：画布上 500 多个节点、近千条连线。按理说这种规模在普通网页编辑器里早就卡成幻灯片，但在这个零框架前端工具里，拖拽、缩放、框选依然跟手。秘诀就是上面的视口剔除加批量测量——屏幕上永远只算"看得见的那部分"。阿杰当时截图发群里："原来本地单文件也能这么稳。"

想深入看实现，可读 README 的 [编辑器核心模块实现原理]([GITHUB_REPO_URL]#核心模块)。

## Coze 工作流 YAML 格式长什么样？

用转换器导出的 YAML，结构清晰、可读、适合 Git。一个最小示例（注意：这是本工具转换出的可读 YAML，非 Coze 官方导出 DSL）：

```yaml
version: "1.0"
kind: Workflow
spec:
  name: 智能客服问答
  nodes:
    - id: start_1
      type: start
      position: { x: 120, y: 80 }
      data:
        outputs:
          - name: user_query
            type: string
    - id: llm_1
      type: llm
      position: { x: 360, y: 80 }
      data:
        model: gpt-4o
        prompt: "回答用户：{{user_query}}"
  edges:
    - source: start_1
      target: llm_1
```

字段说明：

- 顶层：version（格式版本）、kind（固定 Workflow）、spec（工作流主体）。
- nodes：节点数组，每个节点有 id、type、position（坐标）、data（节点参数，如模型名、提示词）。
- edges：连线数组，描述 source → target 的流向与锚点。

YAML 和 JSON 的区别在哪？对 Coze 工作流管理而言，YAML 有三个实在好处：一是对人更可读，缩进即结构；二是支持注释，你可以给某段节点写"为什么这样连"；三是 diff 友好，Git 里改一个模型名就是一行变更，Review 一目了然。JSON 更机器化、更啰嗦，适合程序间传输，不适合人维护。

## 和 Coze Studio / Logic Flow / agentbridge 怎么选？

一张表说清定位差异：

| 维度 | 本项目（零框架单文件） | Coze Studio（官方） | Logic Flow / Drawflow | agentbridge / coze-workflow-parser |
|------|------------------------|---------------------|-----------------------|--------------------------------------|
| 运行环境 | 浏览器单文件，双击即跑 | 需 Docker 部署（[Coze Studio 开源仓库](https://github.com/coze-dev/coze-studio)） | 需前端工程接入 | 命令行（Go/Python） |
| 框架依赖 | 零框架，纯 ES Module | 重框架 | 需框架/构建 | 无 UI |
| 可视化拖拽编辑 | ✅ 原生支持 | ✅ | ✅（通用图形） | ❌ 无 |
| YAML↔Coze 双向转换 | ✅ | ❌ | ❌ | ✅（仅转换） |
| 离线 / file:// 运行 | ✅ | ❌ | 部分 | ✅（CLI） |
| Coze 节点覆盖 | 50 种 | 官方全量 | ~13 类通用 | 解析层 |
| 单文件分发 | ✅ | ❌ | ❌ | ✅（二进制） |

结论很直接：你要官方全量 + 云端协作，选 Coze Studio；你要通用流程图嵌入自己的产品，选 Logic Flow；你要命令行批量解析，选 agentbridge。但你要的是本地、离线、零依赖、能拖拽、能转 YAML、Coze 节点齐全——这个类目里，这个单文件 HTML 工具是目前的空白处。

## 常见问题 FAQ

**Q1：YAML 转 Coze 后还能导回官方平台吗？**

**Q3：支持哪些 Coze 工作流节点类型？**
目前覆盖 50 种，包括 llm、code、knowledge_query、condition、loop、batch、http、db_*、memory、video 等，详见 [Coze 50 种节点类型完整清单]([GITHUB_REPO_URL]#支持的节点类型)。

**Q4：单文件 HTML 拖拽编辑器需要联网吗？**
不需要。file:// 双击即运行，断网也能编辑、转换、导出。

**Q5：开源 Coze 工作流转换器免费吗？许可证是什么？**
MIT 许可证，可自由用于商业与个人项目。

**Q6：大画布会卡吗？**
不会。虚拟滚动 + 视口剔除 + 批量 DOM 测量，500+ 节点实测依旧流畅。
